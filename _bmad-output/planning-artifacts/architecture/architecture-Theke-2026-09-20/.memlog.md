- (direction by user) Fast path basado en supuestos; único entregable: spine técnico.
- (constraint) Se adopta el frontend existente React 19 + TypeScript estricto + Vite + React Flow + Zustand y todas las invariantes de AGENTS.md, incluido container, orden padre-hijo y ausencia de transition-all en resize.
- (assumption) Paradigma: monolito modular con límites hexagonales en integraciones; una sola base operativa Supabase y un único repositorio para web, migraciones, funciones y contratos.
- (decision) La UI depende de casos de uso y contratos; Supabase, Storage, Realtime e IA quedan detrás de adaptadores. Componentes React no consultan tablas ni proveedores directamente.
- (assumption) Backend MVP: Supabase Postgres/Auth/Storage/Realtime/Queues + una Edge Function API TypeScript con Hono; se descarta por ahora un servicio Node separado para minimizar operación.
- (decision) Todos los comandos multi-entidad, operaciones destructivas, publicación, comentarios públicos, uploads y llamadas de IA pasan por API server-side; lecturas privadas simples pueden usar Data API solo mediante src/data y RLS.
- (decision) Modelo híbrido: Recursos y Relaciones canónicos normalizados; cada Diagrama guarda un documento JSONB versionado con Representaciones, Grupos, Anotaciones, presentación y visibilidad local referenciando IDs canónicos.
- (decision) La cuenta/workspace es el tenant de seguridad; cada alta crea una cuenta personal y memberships deja preparada la colaboración futura. Recursos y Relaciones pertenecen a la cuenta; Proyectos seleccionan y organizan referencias.
- (decision) RLS y grants de mínimo privilegio protegen toda tabla y objeto expuesto. Ningún service key llega al navegador; endpoints públicos proyectan DTOs seguros sin acceso anon directo a tablas canónicas.
- (assumption) Autoguardado: documento completo del Diagrama con debounce, base_revision e idempotency key; actualización atómica incrementa revision o devuelve 409. IndexedDB conserva borradores pendientes y nunca reemplaza silenciosamente cambios locales.
- (decision) Zustand posee solo estado local/efímero del Canvas; TanStack Query posee caché remota. Toda mutación estructural entra por comandos del store y se serializa a través del repositorio de Diagrama.
- (decision) Un Compartido almacena token aleatorio solo como hash, allowlist explícita de Recursos y estado. La API pública calcula una proyección viva segura; revocar bloquea resoluciones nuevas. Archivos usan URLs firmadas de vida corta desde buckets privados.
- (assumption) Identidad anónima de comentario: token opaco en cookie HttpOnly Secure SameSite=Lax, hash en servidor y vigencia de 30 días; editar exige misma identidad y Compartido activo.
- (assumption) Antiabuso inicial sin CAPTCHA: límites transaccionales por Compartido, sesión y huella IP HMAC rotatoria; conservar borrador y ofrecer recuperación accesible. Umbrales se fijan en historias y se ajustan con el piloto.
- (decision) Uploads van a bucket privado de cuarentena con clave UUID generada por servidor; MIME/tamaño se validan, se encola inspección y preview, y solo scan_status=clean permite exposición pública. Nombre original es metadato, nunca ruta.
- (decision) Supabase Queues transporta trabajos durables. Edge Functions solo procesan tareas cortas e idempotentes; extracción multimedia o escaneo pesado usa worker sustituible y no bloquea la API.
- (decision) IA es un puerto server-side opt-in. Cada ejecución persiste alcance, recursos/versiones, proveedor/modelo, finalidad, resultado y procedencia; aceptar una sugerencia ejecuta los mismos comandos manuales. Proveedor/modelo quedan diferidos.
- (decision) Realtime se limita a invalidación/notificaciones y comentarios; no transporta comandos ni convierte el MVP en coedición. Postgres sigue siendo autoridad.
- (assumption) Despliegue: Vercel para SPA Vite y Supabase administrado en sa-east-1 São Paulo; local, staging y producción usan proyectos/secretos separados. Preview web usa staging con datos de prueba, nunca producción.
- (decision) Cambios de esquema solo mediante migraciones versionadas en supabase/migrations; ninguna edición manual de producción. Contratos API se validan con Zod compartido y tipos DB se regeneran desde el esquema.
- (decision) Convenciones: UUID v4 opacos, timestamptz UTC/ISO-8601, snake_case en DB y camelCase en DTO/UI; errores API {error:{code,message,details?,requestId}} y éxito {data,meta?}.
- (decision) Outbox/queue se escribe en la misma transacción que cambios que generan jobs o notificaciones; consumidores son idempotentes y registran intentos. No se introduce event sourcing.
- (assumption) Observabilidad: logs JSON con requestId sin contenido de Recursos, Sentry para web/Edge, métricas de autoguardado, latencia pública, errores, cola y AI; eventos de piloto se guardan first-party.
- (decision) Pruebas mínimas: Vitest + Testing Library para dominio/UI, Playwright para UJ-1/UJ-2, pgTAP/supabase test db para RLS, contratos API y escenario de 200 Representaciones/300 Relaciones. CI exige lint, build y suites relevantes.
- (assumption) Antes de piloto externo: plan con backups diarios de DB, exportación verificada y copia periódica de objetos Storage fuera del proyecto; Supabase DB backups no incluyen objetos Storage.
